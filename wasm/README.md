# MD4C for the browser (WebAssembly)

This directory compiles MD4C to WebAssembly, adds a browser file system built
on [storagesdk](https://github.com/storagesdk/storagesdk), and ships a small
blog that renders Markdown in the browser. The blog is fully static: posts
are files in read-only public storage (for example a Cloudflare R2 bucket),
and only the owner, who holds the storage credentials, can publish.

```
wasm/
├── build.sh            compile src/*.c + wrapper to dist/md4c.wasm
├── md4c_wasm.c         wasm entry points (buffer in, HTML out)
├── libc/               tiny freestanding libc (malloc, string, printf...)
├── js/
│   ├── md4c.js         loads md4c.wasm, exposes toHtml() and the flag constants
│   ├── md4c-fs.js      file API on storagesdk: readFile, writeFile, convertFile...
│   ├── url-adapter.js  read-only storagesdk adapter for a public URL (R2, ...)
│   ├── blog-render.js  Markdown rules shared by browser and publish script
│   └── post-format.js  front matter parsing shared by blog and publish script
├── blog/               the blog front end (app.js, render.js, theme.js, style.css),
│                       site.json, sample posts
├── admin/              admin Worker + app: edit and publish from a phone (admin/README.md)
├── scripts/            assemble-blog.mjs (build the site), publish.mjs (owner's tool),
│                       (the build itself: js/site-build.js + js/pages.js)
└── test/               Node tests + an md2html-compatible CLI for the test suites
```

## Quick start

Requirements: `clang` with the WebAssembly backend, `wasm-ld` (from `lld`),
and Node.js 20 or newer. You don't need Emscripten or a WASI SDK.

```sh
cd wasm
npm install
npm run build           # dist/md4c.wasm and the site in dist/blog/
npm run deploy          # publish site + posts to dist/public/ (fs adapter)
python3 -m http.server -d dist/public 8080   # any static server works
# open http://localhost:8080/index.html
```

To build just the wasm module, run `sh wasm/build.sh [out.wasm]`. You can
override the compiler and optimisation flags with `CC` and `OPTFLAGS`.

## Using the renderer

```js
import { loadMd4c, Dialect, Flags } from './md4c.js';

const md4c = await loadMd4c();                 // fetches ./md4c.wasm
md4c.toHtml('# Hello *world*');                // GitHub dialect by default
md4c.toHtml(src, { parserFlags: Dialect.COMMONMARK | Flags.TABLES });
```

`toHtml` accepts a string or UTF-8 bytes and returns a string. Every
`MD_FLAG_*` and `MD_HTML_FLAG_*` constant is available as `Flags.*` and
`HtmlFlags.*`.

## The file system wrapper

The wasm module does no I/O. Where native `md2html` reads and writes files
through stdio, the browser build relies on `md4c-fs.js`, which gives you a
small file API backed by a storagesdk `Storage`:

```js
import { Md4cFs } from './md4c-fs.js';

// In the browser: read-only, over a public URL.
const fs = await Md4cFs.open({ baseUrl: 'https://pub-xxxx.r2.dev/' });
const html = await fs.renderFile('posts/hello.md');
const files = await fs.readdir('posts/');

// Anywhere with a writable storagesdk adapter (fs, R2, S3, ...):
const rw = await Md4cFs.open({ storage: new Storage({ adapter: r2({...}) }) });
await rw.writeFile('docs/intro.md', '# Intro');
await rw.convertFile('docs/intro.md', { fullHtml: true });  // -> docs/intro.html
```

`url-adapter.js` implements the storagesdk adapter interface over plain
HTTP GETs. Every write method throws `NotSupported`. A public bucket URL
can't list its contents, so `list()` and `head()` read an `index.json`.
The publish script can generate it, or you can write a plain list of paths
by hand. `download()` doesn't need the index.

`@storagesdk/core` is plain ESM with no Node dependencies. The site build
copies it into `vendor/` and rewrites the imports to relative paths, so you
don't need a bundler or an inline import map, which the CSP would block.

## The blog

Guests can only read. Nothing on the page can change the storage: there's
no login, no editor and no server code. The owner publishes from their own
machine.

| Who            | How they reach the storage                  | Can do      |
|----------------|---------------------------------------------|-------------|
| Guest          | the bucket's public URL (plain HTTP GET)    | read        |
| Owner (admin)  | storagesdk adapter with write credentials   | read, write |

Storage layout:

| Path              | Contents                                               |
|-------------------|--------------------------------------------------------|
| `index.html`      | home page, pre-rendered with every article as a link   |
| `posts/<slug>.html` | each article, pre-rendered with SEO metadata         |
| `sitemap.xml`, `feed.xml`, `robots.txt`, `theme.css` | generated by `publish.mjs` |
| `app.js`, `lib/`, `vendor/`, ... | the site's code (`publish.mjs --site`)   |
| `index.json`      | `site` settings and the post list (`["posts/a.md"]`)   |
| `posts/<slug>.md` | Markdown with front matter (`title`, `date`, `tags`)   |
| anything else     | images and assets; relative links resolve per post     |

### Publishing

Posts are Markdown files in a local folder (default `blog/posts/`).
`scripts/publish.mjs` uploads them through any storagesdk adapter and then
rebuilds `index.json`:

```sh
node scripts/publish.mjs --to fs                 # local folder dist/public/
node scripts/publish.mjs --to r2 --site          # R2: site + posts
node scripts/publish.mjs --to r2 --posts ~/blog  # only posts, from ~/blog
node scripts/publish.mjs --to r2 --prune         # also delete removed posts
node scripts/publish.mjs --to r2 --no-posts      # only rebuild index.json
node scripts/publish.mjs --to r2 --sources-bucket my-blog-drafts
                                                 # keep the posts' Markdown private
node scripts/publish.mjs --help
```

- Posts with `draft: true` in the front matter are never uploaded. If one
  was published before, it is deleted from storage.
- Posts with `password: …` in the front matter are uploaded encrypted
  (`js/protect.js`). Readers type the password on the post's page to read
  it; see "Password-protected posts" in DEPLOY-CLOUDFLARE.md.
- You can also write files into the bucket directly, with the Cloudflare
  dashboard, `rclone`, the storagesdk CLI or anything else. Run
  `--no-posts` afterwards so `index.json` lists them.
- With `--sources-bucket <private bucket>`, the posts' Markdown goes to that
  bucket (under `.published/`) instead of the public one, which then holds
  only the pages; Markdown already public is moved there. The admin does
  the same with its drafts bucket, so a site published from the admin is
  rebuilt with `--sources-bucket <the drafts bucket>` (without it the
  rebuild is refused rather than deleting the pages).
- Adapters are chosen with `--to` or `STORAGE_ADAPTER` and configured with
  storagesdk's env vars. For the `fs` adapter, `FS_ROOT`/`FS_FOLDER` default
  to `dist/` and `public`.

### Customising the look

The `site` section of `index.json` sets the blog's appearance. Edit it in
the bucket like any other file; readers see the change on their next visit.
Every field is optional:

```json
{
  "site": {
    "title": "Notes on Computation",
    "slogan": "Essays on parsing, compilers and the web platform",
    "author": "Your Name",
    "description": "Shown to search engines and link previews.",
    "theme": "academic",
    "colorScheme": "auto",
    "accent": "#8b1e2d",
    "font": "serif",
    "backgroundImage": "assets/header.jpg",
    "backgroundMode": "hero",
    "stylesheet": "assets/custom.css",
    "numberedHeadings": true,
    "toc": true,
    "graph": true,
    "citation": true,
    "math": true,
    "footer": "© 2026 Your Name · Text licensed under CC BY 4.0",
    "links": [ { "label": "About", "href": "#/post/about" } ]
  },
  "items": ["posts/hello.md", "posts/kyoto.md"]
}
```

| Field | Values |
|---|---|
| `theme` | `academic` (default): journal-style serif typography. `modern`: plain sans-serif. |
| `colorScheme` | `auto` (follow the reader's system), `light` or `dark` |
| `accent` | any CSS colour, used for links and highlights |
| `font` | `serif` or `sans`; the default depends on the theme |
| `backgroundImage` | image URL, relative to the bucket. `backgroundMode` is `hero` (a banner behind the title) or `page` (the whole page, with the text on a paper card). |
| `stylesheet` | your own CSS file in the bucket, loaded after the built-in styles |
| `numberedHeadings` | number sections 1, 1.1, … (posts that number their own headings keep their numbers) |
| `toc` | show a "Contents" box on posts with three or more sections. A post's `# Heading`s (after the title) count as sections: in the body they become second-level headings, since the title is the page's only first-level one. |
| `graph` | links between posts, as in Obsidian. A **Graph** page (graph.html, in the menu) draws every post and link: an article is a dot, a tag a blue diamond ("Show tags"), a post linked to but not written yet a dashed ring, and arrows show which way each link goes (both ends for posts that link to each other). Under each post, **Cross-references** lists the posts it links to and the posts that link to it, each with the sentence the link is in, above a graph of those neighbours. Links are `[[Wiki links]]` (`[[Kyoto trip]]` → posts/kyoto-trip) and ordinary links to other posts (`[text](kyoto.md)`). Password-protected posts keep their links secret. |
| `citation` | show a "How to cite" box with a reference and BibTeX |
| `math` | typeset `$…$` and `$$…$$` with KaTeX, loaded only on posts that use them |
| `links` | extra navigation links: `#/post/<slug>` or an http(s) URL |

Values are validated in the browser. Unknown or malformed values fall back
to the defaults, and text is never treated as HTML. Only http(s) URLs are
used. Nothing is applied as inline style markup, so the strict
Content-Security-Policy stays in force.

The `academic` theme is laid out like a journal:
- small-caps masthead;
- article list with dates, abstracts and keywords;
- centred titles with author, date and reading time;
- numbered sections and a contents box;
- an image on its own line becomes a numbered figure, with its alt text as
  the caption;
- tables with rules above, below and under the header only (booktabs
  style);
- footnotes collected as notes;
- a citation box;
- clean print styles.

It uses Source Serif 4. The font and KaTeX are served from the same bucket,
so readers never contact a third-party CDN.

`publish.mjs` keeps the `site` section when it rebuilds `index.json`. Use
`--config site.json` to replace it from a local file. On the first publish
it starts from `blog/site.json`.

### Tags, dates and search engines

Each post's front matter (`title`, `date`, `tags`, plus the optional
`description`, `image`, `author` and `updated`) feeds both the home page
filters and the search engine metadata:

- **Filters:** the home page groups articles by year and offers search, a
  year menu and tag chips with counts. The state is in the URL
  (`index.html?tag=parsing&year=2025`), so filtered views can be shared.
- **Pre-rendered pages:** `publish.mjs` renders every post to
  `posts/<slug>.html` with md4c.wasm in Node, so crawlers and link previews
  see real content and need no JavaScript. Each page carries a title, a
  description, a canonical URL, Open Graph and Twitter cards, JSON-LD
  (`ScholarlyArticle` or `BlogPosting`) and Google Scholar `citation_*`
  tags.
- **Generated files:** the home page lists every article as a plain link.
  `sitemap.xml`, `robots.txt` and an Atom `feed.xml` are generated too.
  Search-console verification tags come from `site.verification`, and
  `--indexnow` notifies Bing, Yandex and other IndexNow engines.

Set `site.url` to the blog's public address so canonical links, the
sitemap and the feed can use absolute URLs. DEPLOY-CLOUDFLARE.md walks
through Google Search Console and Bing Webmaster Tools.

Pre-rendered pages hold the owner's own content, built on the owner's
machine. They rely on the CSP rather than DOMPurify: no inline script,
event handlers or `javascript:` URLs, and no frames from other origins.
Posts rendered live in the browser (`#/post/<slug>`, before a rebuild)
still go through DOMPurify.

### Editing from a phone

`admin/` adds an admin app on its own hostname, behind Cloudflare Access.
It has a folder explorer, a Markdown editor with live preview in the blog's
theme, photo upload, drafts in a private bucket, and publishing. It runs the
same site build in the browser, while a small Worker checks every write: the
Access identity, allowed paths, create-or-update preconditions, and file,
folder and slug conflicts. See [admin/README.md](admin/README.md).

### Hosting on Cloudflare R2

See [DEPLOY-CLOUDFLARE.md](DEPLOY-CLOUDFLARE.md). In short, the site and the
posts sit in one R2 bucket behind a custom domain, and readers fetch them
over R2's free-egress public URL. You add posts by uploading Markdown and
images to the bucket with the dashboard, wrangler, rclone or
`publish.mjs`, then list them in `index.json`. A hand-written
`["posts/a.md", ...]` is enough.

The R2 adapter needs the AWS S3 SDK packages, which are installed as
optional dependencies. Other storagesdk backends, such as S3, GCS or Azure,
need their own SDKs.

### Security

- **Writes:** guests have no write path at all. The public URL is read-only,
  the page contains no credentials, and `url-adapter.js` refuses writes.
  The only write credentials are the owner's API token.
- **Drafts:** drafts stay on the owner's machine. Anything uploaded to the
  bucket is readable by URL, so the publish script warns if a draft turns up
  there.
- **XSS:** posts may contain raw HTML, so all rendered HTML goes through
  DOMPurify. It removes scripts, event handlers, `javascript:` URLs, iframes
  and forms, and adds `rel="noopener noreferrer nofollow"` to external
  links. This guards against a bad or compromised post.
- **CSP:** a static bucket can't add response headers, so `index.html`
  sets a Content-Security-Policy through a `<meta>` tag (`script-src 'self'
  'wasm-unsafe-eval'`, no inline script or style, `form-action 'none'`).
  It also sets `referrer` to `no-referrer`.
- **Paths:** slugs are limited to lowercase letters, digits and dashes, and
  `..` paths are rejected.

## How the C build works

`build.sh` compiles `src/md4c.c`, `src/md4c-html.c`, `src/entity.c`,
`md4c_wasm.c` and `libc/libc.c` with `--target=wasm32 -nostdlib`. The libc
allocator is a bump arena that `md4c_wasm_reset()` clears before each
conversion. This keeps the allocator tiny and leaves memory use proportional
to the largest document converted. The module imports only one function,
`env.md4c_wasm_log`, which forwards anything MD4C writes to `stderr`.
